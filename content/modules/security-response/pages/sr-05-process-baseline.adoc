**Duration:** ~25 minutes

== Overview

Image hardening takes time to reach every pipeline. Morgan wants a platform control that flags unexpected processes now. Sarah locks the RHACS process baseline for `payment-gateway`, then locks every baseline in the vulnerable-workload namespace through the API.

RHACS uses eBPF probes on each node to see processes that start in a container. No change to the application is required. While a baseline is unlocked, RHACS adds newly observed processes to the list. After the baseline is locked, a process that was not on that list raises *Unauthorized Process Execution*. Detection is on by default. Killing the pod is a later enforcement choice.

== Why it matters

The NetworkPolicy from exercise 2 stops egress. It does not stop a new process from starting inside the container. A locked baseline tells the SOC that `/bin/bash` ran when the workload's normal process is `httpd`.

== Your mission

Show that a shell can run, remove that shell from the learned baseline, lock it, and confirm the violation. Then lock the `vulnerable-workload-{workshop_user_suffix}` baselines with the API token from lab setup.

== Show that a shell can run

[source,bash,subs="+macros,+attributes",role=execute]
----
oc -n payment-gateway-{workshop_user_suffix} exec deploy/payment-gateway -- \
  /bin/bash -c "whoami && hostname && echo 'Arbitrary process execution successful'"
----

The command succeeds. Anyone who can exec can start a process the image did not need for serving traffic.

== See the unlocked baseline

In RHACS, open *Risk* and select deployment `payment-gateway` in namespace `payment-gateway-{workshop_user_suffix}`. Open *Process Discovery*.

The baseline is still unlocked, so the shell you just ran may already be on the list. An unlocked baseline keeps learning. It does not alert.

== Lock the baseline

On *Process Discovery* for `payment-gateway`:

. Remove `/bin/bash` and any other shell you do not want treated as normal. Use the *X* next to that process.
. Leave `httpd` and its workers on the list.
. Click the lock icon.

image::fsi-security/locked1.png[Process discovery before lock,link=self, window=blank, width=100%]

image::fsi-security/locked2.png[Removing a shell from the baseline,link=self, window=blank, width=100%]

image::fsi-security/locked3.png[Locked process baseline,link=self, window=blank, width=100%]

Run the shell again. RHACS detects the process. It does not block it.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc -n payment-gateway-{workshop_user_suffix} exec deploy/payment-gateway -- \
  /bin/bash -c "whoami && hostname && echo 'Can I still do this?'"
----

Open *Violations*. Find *Unauthorized Process Execution* for `payment-gateway`. The detail names `/bin/bash`.

image::fsi-security/locked4.png[Unauthorized process execution violation,link=self, window=blank, width=100%]

image::fsi-security/locked5.png[Violation detail for the shell,link=self, window=blank, width=100%]

Enforcement that kills the pod, or blocks the exec, is a follow-on policy. Detection is the control this exercise turns on.

== Lock a namespace from the API

Locking one deployment in the console does not scale to every workload Morgan wants covered today. The home page setup script saved an API token in `~/.acs-roadshow/env`. You do not need to create another token.

List the clusters, then lock every baseline in `vulnerable-workload-{workshop_user_suffix}`.

[source,bash,subs="+macros,+attributes",role=execute]
----
source ~/.acs-roadshow/env
test -n "$ROX_API_TOKEN"
test -n "$ROX_CENTRAL_ADDRESS"

curl --silent --insecure \
  --header "Authorization: Bearer ${ROX_API_TOKEN}" \
  "https://${ROX_CENTRAL_ADDRESS}/v1/clusters" \
  | jq -r '.clusters[] | "\(.id) \(.name)"'

export CLUSTER_ID="$(curl --silent --insecure \
  --header "Authorization: Bearer ${ROX_API_TOKEN}" \
  "https://${ROX_CENTRAL_ADDRESS}/v1/clusters" \
  | jq -r '.clusters[0].id')"
echo "Locking baselines with cluster ${CLUSTER_ID}"

curl --silent --insecure \
  --header "Authorization: Bearer ${ROX_API_TOKEN}" \
  --header "Content-Type: application/json" \
  --request PUT \
  "https://${ROX_CENTRAL_ADDRESS}/v1/processbaselines/bulk/lock" \
  --data "{\"cluster_id\": \"${CLUSTER_ID}\", \"namespaces\": [\"vulnerable-workload-{workshop_user_suffix}\"]}" \
  | jq .
----

Expect `"success": true`. If more than one cluster is listed, set `CLUSTER_ID` to the cluster that runs your namespaces and run the PUT again.

In *Risk*, baselines for deployments in `vulnerable-workload-{workshop_user_suffix}` show as locked.

== What you learned

* An unlocked baseline learns. A locked baseline alerts when a new process starts.
* The API can lock every baseline in a namespace in one call.
* Image hardening, the deny-egress policy from exercise 2, and process baselining are three separate controls.
