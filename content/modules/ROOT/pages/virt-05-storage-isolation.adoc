:role: Virtualization Storage Isolation
:skills: DataVolume Clone RBAC, Shareable Disks, errorPolicy
:labid: LAB-VIRT-05
:toc:
:toclevels: 1
:icons: font

**Duration:** ~25 minutes

== Overview
xref:virt-04-vm-configuration.adoc[virt-04] locked devices and memory on the VM spec. Storage is the next isolation boundary: who can clone a DataVolume across namespaces, whether a disk is marked `shareable`, and whether I/O errors are `ignore` instead of `stop` or `report`.

Default CDI cloning stays inside one namespace unless a cluster admin creates a RoleBinding that grants `datavolumes/source` to a service account in another project. That binding is the control.

== Why it matters
A clone across namespaces is a data copy the destination owners did not take from a signed registry; they took it from someone else's PVC. Shareable disks without a clustered filesystem corrupt data. `errorPolicy: ignore` hides failed writes so the guest thinks the disk is fine.

== What does it solve

* Project A cloning Project B's gold image and whatever secrets landed on that volume
* Two VMs writing the same disk without SCSI reservations or a clustered FS (see also virt-01 `persistentReservation`)
* Windows clustered FS needing `report`, vs a lab that set `ignore` to quiet logs

== Your Mission
Find RoleBindings that grant DataVolume clone across namespaces, list VMs with `shareable: true`, and list VMs with `errorPolicy: ignore`. Expect empty on a fresh lab. Do not patch `rhel9-vm`.

=== Prerequisites

* xref:virt-04-vm-configuration.adoc[virt-04] complete
* Permission to get RoleBindings, ClusterRoles, and VirtualMachines

Click each step for the full solution.

=== Control: Restrict access to cross-namespace DataVolume cloning (Level 1 Control)

CDI allows a DataVolume in namespace D to clone from namespace S only when S contains a RoleBinding whose subject is a ServiceAccount in D and whose role includes `datavolumes/source`.

*Pros:* Namespace isolation holds for virtual disks, not only for pods. Data does not silently flow to another tenant.

*Cons / impact:* Self-service "copy this gold VM into my project" needs a platform-owned binding or a registry/PVC workflow inside the same namespace.

*Default:* Only cluster administrators can arrange cross-namespace clones. There is no such RoleBinding until someone creates it.

.Audit clone RoleBindings
[%collapsible]
====
`admin` and `edit` include `datavolumes/source` along with every other namespace permission, so they are not clone grants. This audit keeps only roles whose rules are that one resource, then prints bindings of those roles to a ServiceAccount in another namespace.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get clusterrole,role -A -o json | jq -r '
  [.items[]
   | select(any(.rules[]?; any(.resources[]?; . == "datavolumes/source")))
   | select(all(.rules[]?; (.resources | length) > 0 and all(.resources[]?; . == "datavolumes/source")))
   | .metadata.name] | unique | .[]
'
----

[source,bash,subs="+macros,+attributes",role=execute]
----
echo 'Cross-namespace clone bindings:'
LINES=""
if [[ -n "${ROLES}" ]]; then
  ROLE_JSON="$(printf '%s\n' ${ROLES} | jq -R . | jq -sc .)"
  LINES="$(oc get rolebinding,clusterrolebinding -A -o json | jq -r --argjson roles "${ROLE_JSON}" '
    .items[]
    | . as $b
    | select($roles | index($b.roleRef.name))
    | .subjects[]?
    | select(.kind == "ServiceAccount" and .namespace != null and .namespace != ($b.metadata.namespace // ""))
    | "\($b.metadata.namespace // "cluster")/\($b.metadata.name)  role=\($b.roleRef.name)  subject=\(.namespace)/\(.name)"
  ')"
fi
if [[ -z "${LINES}" ]]; then
  echo '  none'
else
  printf '%s\n' "${LINES}"
fi
----

TIP: `Cross-namespace clone bindings: none` is a pass. CDI ships the narrow role `cdi.kubevirt.io:clone-sourcer` so an admin can bind it later; that name on the first list is normal. A hit is one line such as `gold/clone-to-app  role=cdi.kubevirt.io:clone-sourcer  subject=app/default`. That pattern is the textbook finding in the link:https://access.redhat.com/sites/default/files/attachments/rh-openshift-virtualization-hardening-guide-detail-202512-en.pdf[Red Hat OpenShift Virtualization hardening guide^].
====

.Inspect a known cloner ClusterRole (if it exists)
[%collapsible]
====
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get clusterrole datavolume-cloner -o yaml 2>/dev/null || echo "No datavolume-cloner ClusterRole (typical on a default install)"
----

TIP: If the ClusterRole exists, its `rules` should be the clone API only, and RoleBindings that use it should be rare and named.
====

.Remediation
[%collapsible]
====
Delete RoleBindings that grant unintended cross-namespace clone. Do not delete CDI operator Roles.

[source,bash,subs="+macros,+attributes",role=execute]
----
# oc delete rolebinding BINDING -n SOURCE_NAMESPACE
----

TIP: Re-run the audit. `Cross-namespace clone bindings` should say `none`. See link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/virtualization/virt-cloning-a-datavolume[OpenShift Virtualization DataVolume cloning^] for the supported grant procedure when clone *is* required.
====

=== Control: Disable shareable disks (Level 1 Control)

`shareable: true` on a disk lets more than one VM attach it. That is valid only with a clustered filesystem or a distributed application that understands shared block.

*Pros:* No silent dual-write corruption. Each disk has one writer unless you opted into clustered I/O.

*Cons / impact:* You cannot use shared-block clustering without this flag (and often without `persistentReservation` from virt-01). Treat that as a named exception.

*Default:* Shareable is off. The VM list should be empty.

.Audit shareable disks
[%collapsible]
====
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get vm -A -o json | jq -r '
  .items[]
  | select([.spec.template.spec.domain.devices.disks[]? | select(.shareable == true)] | length > 0)
  | .metadata.namespace + "/" + .metadata.name
'
----

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get vm rhel9-vm -n rhacs-virt -o json | jq '
  [.spec.template.spec.domain.devices.disks[]? | {name, shareable}]
'
----

TIP: First command empty. Second command: disks with `shareable` null or `false`.
====

.Remediation
[%collapsible]
====
Remove the flag on disk index 0 of a VM you own (not `rhel9-vm`):

[source,bash,subs="+macros,+attributes",role=execute]
----
# oc patch vm VM_NAME -n NAMESPACE --type='json' -p='[
#   {"op": "remove", "path": "/spec/template/spec/domain/devices/disks/0/shareable"}
# ]'
----

TIP: Re-run the cluster `jq`. The VM should drop off the list.
====

=== Control: Make sure errorPolicy is not ignore (Level 1 Control)

Disk `errorPolicy` decides what happens on a failed read/write. `ignore` continues as if the I/O succeeded. `stop` (default) pauses the VM. `report` surfaces the error to the guest (needed for some Windows clustered filesystems).

*Pros:* Failed writes become an incident, not silent corruption.

*Cons / impact:* Noisy storage may pause VMs (`stop`) instead of hiding errors. Maintenance windows that set `ignore` to reduce logs are a temporary exception, not a baseline.

*Default:* Unset, which means `stop`. The ignore-list should be empty.

.Audit errorPolicy ignore
[%collapsible]
====
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get vm -A -o json | jq -r '
  .items[]
  | select([.spec.template.spec.domain.devices.disks[]? | select(.errorPolicy == "ignore")] | length > 0)
  | .metadata.namespace + "/" + .metadata.name
'
----

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get vm rhel9-vm -n rhacs-virt -o json | jq '
  [.spec.template.spec.domain.devices.disks[]? | {name, errorPolicy}]
'
----

TIP: First command empty. Second: `errorPolicy` null or `stop`/`report`, never `ignore`.
====

.Remediation
[%collapsible]
====
Remove a bad policy (revert to default `stop`) or set `report` when Windows clustered FS needs it.

[source,bash,subs="+macros,+attributes",role=execute]
----
# oc patch vm VM_NAME -n NAMESPACE --type='json' -p='[
#   {"op": "remove", "path": "/spec/template/spec/domain/devices/disks/0/errorPolicy"}
# ]'
----

TIP: The VM should leave the ignore-list. Prefer `report` over `ignore` for clustered Windows disks; do not use `ignore` as the fleet default.
====

== Debrief

Storage isolation is RBAC (clone), shared-writer flags, and honest I/O errors. Combined with virt-01 persistent reservations, you now have the clustered-disk story: off unless Windows shared FS is a documented exception.

What breaks without this:

* Tenant B reading tenant A's disk via clone
* Dual-write corruption on a "shared" PVC
* Guests that never see a failed write
